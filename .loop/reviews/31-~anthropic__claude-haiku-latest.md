# ADVISORY REVIEW: langchain-php

## 1. MessageMerge::mergeContent() succeeds on incompatible second-side block types
**Severity:** MAJOR
**Evidence:** `MessageMerge::mergeContent()` recursively coerces a string first side into blocks, then calls `mergeLists()` on the two block arrays. `mergeLists()` has no type validation on blocks — it calls `findMergeTarget()` on each incoming item, which succeeds silently for any array with an `index` or `id` key, then calls `mergeDicts()` on the accumulated value. A block with `type: "unsupported_type"` passes through because `mergeDicts()` concatenates the `type` field (first wins, so the existing type is kept) and merges everything else. This means a provider that returns an unknown block type alongside text silently corrupts the message by folding into an existing text block.
**Why it matters:** A custom provider or an Anthropic streaming event that happens to include an unfamiliar content-block type will merge into text rather than being refused or logged, producing a message that *looks* decoded and is wrong.
**Suggested fix:** In `mergeLists()` at the top of the loop over `$right`, add a guard: if `is_array($item)` and `isset($item['type'])` and that type is not in a whitelist of known types (TEXT, IMAGE, TOOL_CALL, etc.), either log a notice or throw. The whitelist should live in `ContentBlock`.

## 2. convertToChunk() does not preserve the message's additional_kwargs aliases
**Severity:** MINOR
**Evidence:** `MessageUtils::convertToChunk()` builds `$base` from the message's `content`, `additional_kwargs`, `response_metadata`, `id`, and `name`, then creates a chunk from that. But `additional_kwargs` on a message may include provider-specific keys like `function_call` (OpenAI) or `stop_reason` (Anthropic). The chunk carries these through in `$base['additional_kwargs']`, and when later converted back to a message via `AIMessageChunk::toMessage()`, those kwargs are preserved. However, if a caller reads chunk.additional_kwargs expecting to find the fields that were on the original message, they will find them — but if any code normalizes keys (e.g., snake_case to camelCase) between message and chunk, that normalization is lost. This is not a functional break in the common path, but it means calling code cannot reliably round-trip provider-specific fields through a chunk and back.
**Why it matters:** Streaming reconstructed messages may lose provider-specific metadata that was on the original, causing tracer plugins or custom code that inspects `additional_kwargs` to see an incomplete picture.
**Suggested fix:** Document that `additional_kwargs` is opaque and not guaranteed to survive chunk round-trips, OR add a test that asserts a message's `additional_kwargs` are identical to those on the chunk reconstructed from it.

## 3. BaseMessage constructor accepts a bare dict of mixed blocks without validating them
**Severity:** MINOR
**Evidence:** `BaseMessage::__construct()` accepts `string|array $fields`. If `$fields` is an array that `looksLikeFieldMap()` returns false for, the path `$isBareContent = true` and the array is treated as content. If that array is meant to be a single malformed block (e.g., `['type' => 'text', 'bad_key' => 'value']` with no `text` key), it will be stored directly in `$this->content` without any validation. A downstream call to `contentBlocks()` will return it as-is, and a call to `ContentBlock::text()` on it will fail. The issue is that a message can be constructed in a state where its content is invalid, caught only when that content is later read.
**Why it matters:** A caller hand-building a message with a typo in a block key (e.g., `'txt'` instead of `'text'`) will not catch the error at construction time, and the message will appear valid until serialization or rendering tries to read it.
**Suggested fix:** In the bare-content path, if `$fields` is an array and `looksLikeFieldMap()` is false, validate that every element is either a string or a valid block (has a `type` key and passes `ContentBlock::isBlock()`). Blocks with missing required keys should throw at construction.

## 4. Chunk-to-message conversion does not validate the accumulated tool calls
**Severity:** MINOR
**Evidence:** `AIMessageChunk::parseToolCalls()` decodes each chunk's accumulated JSON args and validates the structure, placing invalid ones in the `$invalid` list. It then calls `toMessage()` which creates an `AIMessage` passing both `tool_calls` and `invalid_tool_calls`. However, `AIMessage::__construct()` has no validation that these two arrays contain the expected keys (`name`, `args`, `id`) — if `parseToolCalls()` returns a malformed call, it reaches the message as-is. The comment at line ~370 in `AIMessageChunk.php` states "Chunks whose args do not parse as JSON become invalid tool calls rather than being silently dropped", but a call whose `name` is missing or whose `id` is not a string would be accepted into `$invalid` without further validation.
**Why it matters:** A malformed tool call (missing `name`, wrong type for `id`) can propagate to stored runs and agent traces, where consumers may crash when trying to use it (e.g., `Tool::call()` expects a string name).
**Suggested fix:** In `parseToolCalls()`, after building a call dict for the `$calls` list, validate that `name` is a non-empty string and `id` (if present) is a string. Do the same for items added to `$invalid`. Invalid items with missing keys should be rejected outright or logged.

## 5. AIMessageChunk concat does not preserve tool_call_id from ToolMessageChunk
**Severity:** MINOR
**Evidence:** `AIMessageChunk::concat()` handles merging two AI chunks by calling `MessageMerge::mergeLists()` on `toolCallChunks`. However, when an `AIMessageChunk` is folded with data from a different chunk type (if such a scenario occurs in streaming), the concat is type-checked with `assertSameChunkClass()` and will throw — which is correct. But the issue is that `MessageUtils::convertToChunk()` on a `ToolMessage` produces a `ToolMessageChunk`, which has a `tool_call_id` field. If a stream produces both AI chunks and tool chunks (unlikely but possible in an agent loop), the code path never reaches `AIMessageChunk::concat()` because the chunks are different classes. This is not a bug in the concat logic itself, but rather a gap in the design: there is no defined way to merge an AI chunk with a tool chunk, and the type check prevents it silently.
**Why it matters:** If a streaming scenario ever interleaves AI and tool chunks (e.g., a tool call from the model followed by its result in one stream), the accumulation will fail silently because chunks of different types cannot be merged.
**Suggested fix:** Document in `BaseMessageChunk::concat()` that chunks must be of the same type and that interleaved-type streams are not supported. OR, if such streams are possible, implement a merging strategy in `MessageMerge` that can combine AI and tool chunks by appending rather than folding.
